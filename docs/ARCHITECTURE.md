# ARCHITECTURE.md
## سجل القرارات المعمارية (Architecture Decision Records) — نظام Beauty
### مرجع سريع لأي شخص ينضم للمشروع لاحقًا (فريق تطوير، مستشار تقني، مستثمر)

> هاد الملف بيوثّق **كل قرار تقني اتخذناه فعليًا**، والسبب وراه. الهدف: أي حد جديد يفهم "ليش النظام مبني هيك" بسرعة، بدون ما يرجع لمئات رسائل المحادثة.

## ADR-001: قاعدة البيانات — PostgreSQL عبر Supabase

**القرار:** استخدام Supabase (خدمة مبنية فوق PostgreSQL) بدل قاعدة بيانات منفصلة تُدار يدويًا.

**السبب:**
- PostgreSQL قاعدة بيانات علائقية ناضجة وموثوقة، تدعم كل الميزات المتقدمة يلي احتجناها (Row Level Security، Triggers، JSON columns).
- Supabase وفّر تسجيل دخول (Authentication) جاهز، تخزين ملفات (Storage)، وواجهة إدارة بصرية — بدون ما نبني هاي الأجزاء من الصفر.
- مناسب لمرحلة MVP بفريق صغير/مؤسس واحد — بدون تعقيد إدارة سيرفر قاعدة بيانات بشكل مستقل.

**البديل المرفوض:** قاعدة بيانات منفصلة لكل صالون (Database-per-tenant) — نفس الغلطة المعمارية الموثقة بالنظام الأصلي (Beauty Pro/AIHELPS) يلي درسناها، وسبّبت له "تجمّد معماري" لسنين.

## ADR-002: Multi-Tenancy — Shared Schema مع عزل عبر `salon_id`

**القرار:** قاعدة بيانات واحدة مشتركة لكل الصالونات، مع عمود `salon_id` بكل جدول حساس، وعزل مفروض عبر Row Level Security — مش قاعدة بيانات منفصلة لكل عميل.

**السبب:**
- يسمح بتحديث بنية النظام (Schema) مرة واحدة لكل العملاء دفعة وحدة مستقبلًا.
- أرخص وأسهل صيانة من عشرات/مئات قواعد البيانات المنفصلة.
- هاد بالضبط القرار المعماري يلي ميّزنا عن النظام الأصلي القديم (2012) يلي درسناه.

**التطبيق:** جدول `salons` (كيان الصالون) + جدول `profiles` (يربط كل مستخدم مسجّل دخول بصالون واحد) + عمود `salon_id` بجدول `clients`.

## ADR-003: تسجيل الدخول — Supabase Auth (Email + Password)

**القرار:** استخدام نظام تسجيل الدخول الجاهز من Supabase بدل بناء نظام مصادقة (Authentication) خاص من الصفر.

**السبب:** بناء نظام تسجيل دخول آمن من الصفر (تشفير كلمات السر، إدارة الجلسات، استرجاع كلمة السر) عمل متخصص ومعقّد — لا داعي لإعادة اختراعه لمشروع بحجمنا.

---

## ADR-004: الصلاحيات وعزل البيانات — Row Level Security (RLS)

**القرار:** فرض قواعد الوصول للبيانات على مستوى قاعدة البيانات نفسها (RLS)، مش على مستوى كود التطبيق (Frontend) بس.

**القاعدة الفعلية المطبّقة:**
```sql
using (salon_id = (select salon_id from profiles where id = auth.uid()))
```

**السبب:** لو الاعتماد كان بس على كود الواجهة لمنع مستخدم من رؤية بيانات صالون تاني، أي شخص عنده معرفة تقنية بسيطة كان يقدر يتجاوزها. فرض القاعدة بقاعدة البيانات نفسها يضمن الحماية **حتى لو حدا حاول يتلاعب بالطلبات مباشرة**، مش بس عبر الواجهة.

## ADR-005: سجل التدقيق — Database Trigger بدل كود تطبيق

**القرار:** تسجيل كل عملية إضافة/تعديل/حذف بجدول `clients` تلقائيًا عبر Trigger بقاعدة البيانات (جدول `audit_log`)، مش عبر سطر كود إضافي بكل عملية بالتطبيق.

**السبب:** الـTrigger بيشتغل **بغض النظر عن مصدر التعديل** (موقعنا، أو أي أداة توصل لقاعدة البيانات مباشرة مستقبلًا) — أضمن من الاعتماد على "تذكّر" إضافة سطر تسجيل بكل مكان بالكود يعدّل بيانات.

## ADR-006: البنية العامة للتطبيق — Modular Monolith

**القرار:** تطبيق واحد متكامل (Next.js) مقسّم منطقيًا لموديولات، **مش** خدمات مصغّرة منفصلة (Microservices).

**السبب:** Microservices تحل مشاكل حجم ضخم جدًا (فرق عمل كبيرة، حِمل هائل) — بتكلفة تعقيد تشغيلي كبير (نشر منفصل لكل خدمة، تنسيق بينهم). لمشروع بمرحلة MVP بفريق صغير، هاي التكلفة غير مبررة. القرار قابل لإعادة النظر **لاحقًا فقط لو ولما** يثبت النمو الفعلي حاجة حقيقية لذلك.

## ADR-007: التطوير — فروع Git منفصلة + Commits تدريجية

**القرار:** أي تعديل بالكود يصير على فرع (Branch) منفصل، يُختبر محليًا، وبعدين يندمج (Merge) بـ`main` — مش تعديل مباشر على `main`. كل مرحلة عمل صغيرة تُحفظ بـCommit منفصل.

**السبب:** يسمح بالرجوع لنقطة سليمة سابقة لو صار خطأ بمرحلة لاحقة، بدل ما نخسر كل الشغل أو نضطر نبدأ من الصفر.

**أمثلة فعلية:** `refactor/split-components`، `fix/nextjs-security-update`.

## ADR-008: نظام التصميم — الانتقال لـ shadcn/ui + Tailwind CSS

**القرار:** توحيد كل شاشات النظام تحت مكتبة تصميم واحدة (shadcn/ui) بدل تصميم كل شاشة يدويًا بأنماط مختلفة.

**السبب:** التصميم اليدوي المتكرر (Inline styles) لكل شاشة أدّى لعدم اتساق بصري واضح (لاحظناه فعليًا بعد بناء عدة نسخ تصميم مختلفة). مكتبة موحّدة تضمن **اتساق تلقائي** بين أي شاشة جديدة نضيفها مستقبلًا.

## ADR-009: البيانات الحساسة — بدون تشفير حاليًا (قرار مؤقت موسوم بوضوح)

**القرار:** حقول حساسة (رقم جواز السفر، الرقم التعريفي) مخزّنة كنص عادي حاليًا بمرحلة الـMVP.

**⚠️ هاد قرار مؤقت غير آمن للإطلاق الفعلي** — موسوم صراحة بالكود والتوثيق، ولازم يُعالج (تشفير حقيقي) قبل أي استخدام إنتاجي حقيقي ببيانات زبائن فعليين.

## ADR-010: نموذج بيانات الرصيد المالي — قيمة مُشتقة من سجل حركات (Ledger)

**القرار:** رصيد الزبون المالي لازم يُحسب دايمًا من مجموع سجل حركات منفصل (Ledger)، مش يُعدَّل مباشرة كحقل ثابت.

**السبب:** يمنع تضارب البيانات لو صارت عمليتين متزامنتين على نفس الزبون، وبيوفّر تلقائيًا سجل تدقيق كامل لكل حركة مالية.

## ADR-011: عدم البدء بتوثيق معماري ضخم قبل الكود (قرار منهجي واعٍ)

**القرار:** بناء أصغر جزء شغّال حقيقي أولًا (موديول الزبائن كامل)، بدل كتابة وثيقة معمارية شاملة (100-200 صفحة) قبل أي كود.

**السبب:** التوثيق الشامل المسبق بيفترض معرفة كاملة بكل التفاصيل قبل التجربة الفعلية — غالبًا بتكتشف تفاصيل حقيقية (زي حقول ناقصة، قواعد عمل دقيقة) بس وانت شغّال فعليًا، مش وانت بترسم مخططات نظرية. **هاد الملف نفسه مثال على التوثيق الصحيح: بعد الشغل، مش قبله.**

---

## ADR-012: عمليات الرصيد السريعة — مكانين فقط، مش كل صف بالجدول

**القرار:** رفض إضافة أيقونات "إضافة/خصم رصيد" بجانب كل صف بجدول قائمة الزبائن العامة، بعد ما جُرِّبت فعليًا. عمليات الرصيد السريعة محصورة بمكانين فقط: صفحة ملف الزبون الكامل، والقائمة الفرعية تحت قسم "الزبائن" بالشريط الرئيسي.

**السبب:** التجربة الفعلية أظهرت إنه إضافة نصين/أيقونتين لكل صف بعمود "إجراء" واحد (جنب زر "التفاصيل" الموجود أصلًا) بتكسر إيقاع الجدول البصري وبتزحمه، خصوصًا مع وجود عمود "الرصيد" أصلًا كرقم واضح — تكرار وظيفي بصري بدون فايدة حقيقية تعادل كلفته الجمالية. **درس منهجي:** بعض القرارات التصميمية ما بتبان مشكلتها إلا بعد تجربة فعلية بالمتصفح، مش بالوصف النظري وحده — لهيك مبدأ "خطوات صغيرة + تجربة فعلية قبل الدمج" (ADR-007) حمانا من دمج شي كان لازم نتراجع عنه بعد النشر.

## ADR-013: نمط التنقّل الرئيسي — شريط أفقي موحّد + مكوّن بحث زبون قابل لإعادة الاستخدام

**القرار:** الشريط الرئيسي المشترك (AppShell) تخطيطه أفقي بعرض الشاشة الكامل من فوق (مش عمودي جانبي)، مطابق لبنية المرجعية الأصلية (Beauty Pro). كل قسم مفعّل (زي "الزبائن") بيظهر تحته صف ثابت من اختصارات بأيقونة+نص، جزء من التخطيط نفسه — مش قائمة منسدلة عائمة (Dropdown).

الاختصارات يلي بتحتاج تحديد زبون (تعديل زبون، إضافة رصيد، خصم رصيد) بتستخدم **نفس مكوّن البحث بمرحلتين** (بحث ثم اختيار) المبني أصلًا لقسم "الأقارب والمعارف" — بدون تكرار منطق البحث بمكان جديد.

**السبب:** توحيد نمط التنقّل عبر كل النظام بمكوّن مشترك واحد (AppShell) يضمن اتساق بصري تلقائي لأي صفحة جديدة تُضاف لاحقًا (نفس فلسفة ADR-008). وإعادة استخدام مكوّن البحث بدل بناء بحث جديد لكل ميزة تحتاج "اختيار زبون" يقلّل الكود المكرر ويضمن سلوك متسق (نفس تجربة البحث بكل مكان بالنظام).

**ملاحظة تنفيذية:** أول محاولة بناء لهاي الميزة طبّقت القائمة الفرعية كـDropdown عائم فوق الشريط الجانبي العمودي القديم (بدل التحويل الفعلي لأفقي) — تم رفضها بعد المراجعة البصرية وإرسال توضيح تصميمي أدق مع صورة مرجعية، لتوضيح إنه التغيير مطلوب بالتخطيط نفسه (AppShell) مش بإضافة طبقة فوقه.

## ADR-014: تعدد اللغات (i18n) — بنية مبكرة قبل تراكم الديّن التقني

**القرار:** بناء طبقة i18n (مكتبة قياسية بـNext.js) ونقل كل النصوص العربية الحالية من داخل الكود لملف ترجمة منفصل — **قبل** البدء بموديول الحجوزات، مش بعده ومش بمنتصف الشغل الحالي.

**السبب:** كل شاشة جديدة تُبنى بنص عربي مباشر بالكود بتزيد حجم "الديّن التقني" يلي لازم يُعالج لاحقًا (سحب كل نص لملف ترجمة). التكلفة تتضاعف تقريبًا مع كل موديول جديد، بينما تكلفة الحل الآن (على ~5 شاشات مبنية فقط) محدودة. **التوقيت المعتمد:** بعد إقفال موديول الزبائن بالكامل (checkpoint طبيعي بالخطة)، وقبل أول سطر كود بموديول الحجوزات — لتفادي بناء شاشات جديدة إضافية بالطريقة القديمة.

**نطاق القرار الحالي:** بناء البنية ونقل النصوص العربية الموجودة لملف ترجمة واحد فقط — **بدون** ترجمة فعلية للغة ثانية بعد (هاد يُقرَّر لاحقًا حسب الحاجة الفعلية).

## ADR-015: التوسع لقطاعات أخرى (فيتنس، طب أسنان...) — مؤجّل بوعي، مش قرار هندسي اليوم

**القرار:** عدم بناء تجريد "متعدد القطاعات" (Multi-vertical Abstraction) بالجداول أو الكود بهاي المرحلة.

**السبب:** بناء تجريد يغطي عدة قطاعات مختلفة (خدمة تجميل ≠ جلسة علاج أسنان ≠ اشتراك فيتنس) بدون معرفة فعلية بالفروقات الدقيقة بينهم هو **Over-engineering** — خطر بناء تعقيد لسيناريو افتراضي قد يختلف كليًا عن الاحتياج الحقيقي وقت التوسع الفعلي. هاد قرار عمل استراتيجي (يعتمد على نجاح المنتج بقطاع واحد أول)، مش قرار هندسي يُتّخذ بمرحلة MVP بدون بيانات.

**الانتباه الوحيد المطلوب حاليًا (احتياط منخفض الكلفة، مش بناء فعلي):** الحفاظ على تسمية عمومية للجداول الجوهرية (`salons`, `clients`) بدل أسماء مقفولة حصرًا على مصطلحات صالونات التجميل، وتجنّب حقول بالجداول الأساسية مقفولة بشدة على منطق قطاع واحد.

## ADR-016: مكوّنات i18n مشتركة — كل صفحة لازم تُعلن كل الـnamespaces يلي بتحتاجها

**القرار:** أي مكوّن React مشترك بين أكتر من صفحة (زي `ClientBalanceSummary`, `ClientRelationships`) يستخدم `namespace` ترجمة معيّن، **كل صفحة تستضيفه** (عبر `getServerSideProps`/`getStaticProps`) لازم تُعلن صراحة نفس الـnamespace بقائمتها — حتى لو الصفحة نفسها ما بتحتاج نصوص هاد الـnamespace مباشرة.

**السبب (خطأ حقيقي صار واتحلّ):** أثناء تطبيق i18n على صفحة ملف الزبون، مكوّنات الرصيد والأقارب اشتغلت صح 100% بصفحة `/clients/[id]` (لأنها أعلنت الـnamespace `clientProfile` صراحة)، بس **نفس المكوّنات بالضبط** ظهرت فيها مفاتيح ترجمة خام (`relationships.title`...) لما استُخدمت داخل نافذة منبثقة (Quick View) بصفحة `/` — لأنه تلك الصفحة كانت طالبة بس `common, login, clientsList, clientForm` بدون `clientProfile`. السبب الجذري: `next-i18next` بيحمّل الترجمات على مستوى **الصفحة**، مش على مستوى **المكوّن** — فمكوّن مشترك ما بيجيب ترجماته تلقائيًا أينما استُخدم.

**التشخيص استغرق عدة جولات** (فرضيات كاش متصفح، كاش سيرفر، كاش بناء `.next/cache` — كلها كانت فرضيات معقولة بس غلط) قبل ما ينكشف السبب الحقيقي، لأنه ظاهرة "بعض المكوّنات تتعطّل وبعضها لأ بنفس الصفحة" مش بديهية أول وهلة.

**الإجراء الدائم من هلق:** أي مكوّن مشترك جديد (خصوصًا Dialogs/Modals قابلة للفتح من أكتر من صفحة، زي `BalanceDialog`) — **قبل الدمج**، تُفحص كل صفحة تستخدمه للتأكد من إعلان الـnamespace الصح، مش الاكتفاء بتجربته من صفحة واحدة فقط.

## ADR-017: العمل بدون إنترنت (Offline-first) + مزامنة لاحقة — مخطَّط له مستقبلًا، مش قرار هندسي اليوم

**القرار:** تأجيل بناء "العمل بدون إنترنت + مزامنة تلقائية عند عودة الاتصال" كمشروع هندسي مستقل، **بعد** ما تنضج الوحدات الجوهرية (الفئات، الحجوزات، المبيعات) وتثبت المنتج نفسه بالسوق — مش هلق.

**السبب:** هاد ليس "تغليف Electron بسيط" — فعليًا بيتطلب: (1) قاعدة بيانات محلية كاملة على جهاز كل صالون، (2) محرّك مزامنة (Sync Engine) بين النسخة المحلية والسحابية، (3) منطق حل تعارضات (Conflict Resolution) عند تعديل نفس السجل من أكتر من جهاز أثناء انقطاع الاتصال، (4) مزامنة الملفات/الصور بالإضافة للبيانات النصية. **حجم هندسي أكبر من كل الشغل المبني لهلق مجتمعًا.** والأخطر: أي خطأ بمنطق المزامنة على جدول `client_ledger` (رصيد مالي حقيقي) يعني خطأ مالي فعلي بحساب زبون، لا مجرد خلل بصري — هاد النوع من الميزات ما يُبنى تجريبيًا، بيحتاج تصميم دقيق واختبار مكثّف مستقل.

**الدافع موثّق ومشروع (مش مرفوض):** انقطاع الإنترنت متكرر بصالونات كتير بالسوق المحلي، وهاي ميزة تنافسية حقيقية محتملة (منافسون زي Fresha/Booksy/Zenoti كلهم سحابيون بحتون).

**الإجراء الاحترازي الوحيد المطلوب من الآن (رخيص، بدون بناء المزامنة فعليًا):** كل جدول جديد يُبنى من هلق فصاعدًا (خصوصًا موديول الحجوزات القادم) يُصمَّم بأسلوب "يسهل توفيقه لاحقًا" — بالتحديد **نمط Append-only/Event Log بدل الكتابة فوق قيمة موجودة** (نفس فلسفة `client_ledger` أصلًا بـADR-010: سجل حركات تراكمي، مش رقم يُستبدل). هاد ما بيكلّف شي إضافي هلق، وبيخلي بناء المزامنة لاحقًا أسهل بكتير وأقل عرضة لتعارضات.

**عند حين تنفيذ هذا القرار فعليًا لاحقًا:** يحتاج مراجعة وفحص مستقل إضافي، بالذات حول أي جدول مالي (`client_ledger`)، قبل اعتماده ببيانات صالونات حقيقية.

## ADR-018: مراجع محذوفة بفورمة مفتوحة (Stale Foreign Key) — درس لكل موديول فيه علاقات Lookup

**القرار:** أي فورمة بتحمّل قيمة تشاور على جدول lookup منفصل (فئة، مصدر اكتساب، ولاحقًا: خدمة، موظف، نوع حجز...) لازم تتعامل بأمان مع احتمال إن تلك القيمة تُحذف من مكان تاني بينما الفورمة لسا مفتوحة — إما بإعادة تحميل القيم الحالية قبل الحفظ، أو بمعاملة أي مرجع غير موجود كـ"بدون قيمة" تلقائيًا، بدل ما تحاول ترسله وتفشل.

**السبب (خطأ حقيقي صار واتحلّ):** لما فورمة تعديل زبون كانت مفتوحة ومحمّلة بفئة معيّنة، وانحذفت تلك الفئة من نافذة "إدارة الفئات" بمكان تاني بنفس الوقت، الضغط على "حفظ" حاول يرسل معرّف الفئة القديم (المحذوف) لقاعدة البيانات — فرفضته بخطأ قيد Foreign Key، مع خلل بصري إضافي (عرض UUID خام بدل اسم الفئة).

**لماذا هذا الدرس أهم بموديول الحجوزات القادم:** موديول الحجوزات هيكون مليان بعلاقات Lookup مشابهة (خدمة، موظف/Professional، نوع خدمة...)، وسيناريو "فورمة حجز مفتوحة بينما حدا تاني يحذف موظف أو خدمة بمكان تاني بنفس اللحظة" أكتر احتمالًا بكتير من موديول الزبائن (تعدد مستخدمين يشتغلوا بنفس الوقت على حجوزات مختلفة). **يجب فحص هذا السيناريو صراحة لكل علاقة Lookup جديدة بالحجوزات قبل الاعتماد عليها.**

## ADR-019: نوع النشاط (`business_type`) مرن على أي مستوى بالشجرة — "أقرب أب محدّد له نوع"

**القرار:** إلغاء القيد الصارم الأصلي (فئة رئيسية = إجباري نوع نشاط، فئة فرعية = ممنوع)، واستبداله بقاعدة: أي فئة بأي عمق ممكن تحمل `business_type` مستقل، وإلا ترث من أقرب أب فوقها محدّد له نوع؛ فئة بلا أي جذر محدّد = "عامة" تظهر لكل الأدوار.

**السبب:** القيد الصارم كان يمنع فئات تنظيمية مختلطة (مثال حقيقي: مجلد "باقات عرايس" يجمع فروعًا من شعر ومكياج وأظافر) من العمل صحيحًا مع فلترة الأدوار — فرع "مكياج عروس" تحت جذر غير مصنّف كان يختفي من كل الأدوار بدل أن يظهر لخبيرة المكياج. المرونة الجديدة تحل هذا دون كسر أي بيانات موجودة (الكتالوج الحالي: جذور مصنّفة + فروع فارغة = نفس سلوك الوراثة تلقائيًا).

## ADR-020: ربط دور الموظف بفئات الخدمات (`role_business_types`) — جدول نظام عام لا بيانات صالون

**القرار:** جدول `role_business_types` (دور ↔ نوع نشاط) **بدون** `salon_id`، وبصلاحية **قراءة فقط** من التطبيق (صفر سياسات إدخال/تعديل/حذف) — التعديل الوحيد يصير يدويًا عبر SQL Editor.

**السبب:** هذا العكس تمامًا من كل جدول Lookup سابق (فئات، مصادر اكتساب) الذي كان قابلاً للتخصيص لكل صالون — لأن علاقة "دور↔فئة خدمات" منطق عمل عام لكل النظام (خبير مكياج بيقدّم مكياج بغض النظر عن الصالون)، لا تفضيل صالون فردي. منع الكتابة من التطبيق بمستوى RLS (لا مجرد اتفاق برمجي) يحمي هذه القاعدة النظامية من أي تعديل غير مقصود مستقبلًا.

## ADR-021: الموظف (`employees`) مستقل تمامًا عن حساب تسجيل الدخول (`profiles`)

**القرار:** `employees.profile_id` عمود اختياري (nullable) بـ`ON DELETE SET NULL` — موظف يقدر يوجد بالنظام (يظهر بالتقويم، يُحجز له) بدون أي حساب دخول إطلاقًا.

**السبب:** صالون قد يملك أخصائية ما تحتاج تدخل على النظام أبدًا (تقنية تدليك مثلاً)؛ ربط "الموظف" إجباريًا بحساب دخول كان سيفرض عبئًا (إنشاء حساب دخول لكل موظف حتى لو لم يحتَجه) لا مبرر تجاري له. نفس فلسفة `SET NULL` المستخدمة سابقًا لعلاقات "خسارتها بسيطة" (فئة الزبون).

## ADR-022: دوام الموظف — جدولان مرنان (`employee_schedules` + `employee_schedule_slots`) يدعمان 3 أنماط

**القرار:** بدل عمود لكل نمط دوام (فراغات كثيرة حسب النمط المختار) أو 3 جداول منفصلة (يعقّد أي سؤال بسيط لاحقًا "هل الموظف شغّال الآن؟")، جدولان: `employee_schedules` (نوع النمط + حقول خاصة بنمط `cycle` فقط، مفروضة بـ`CHECK`) و`employee_schedule_slots` (الفترات الفعلية، بمفتاح `slot_key` متغيّر المعنى حسب النمط — `'0'..'6'` لأسبوعي، `'even'/'odd'`، أو `'work'` لدوري).

**السبب:** البديلان المرفوضان تم تحليلهما صراحة قبل التنفيذ (راجع الشرح الكامل بالمحادثة الأصلية) — عمود-لكل-نمط يهدر مساحة ويصعّب الفهم، وجداول منفصلة تعقّد أي استعلام يحتاج معرفة النمط أولاً قبل معرفة أين يبحث. الثمن المقبول: `slot_key` عمود نصي عام لا Enum مضبوط المعنى — ثمن أخف من تعقيد 3 جداول.

## ADR-023: تسعير الخدمة حسب الدور (`service_role_prices`) — جدول استثناءات، لا مصفوفة إجبارية

**القرار:** صف بجدول `service_role_prices` يُضاف فقط عندما يستحق دور معيّن سعرًا مختلفًا عن السعر الأساسي لخدمة معيّنة؛ غياب الصف = يُعتمد `services.price` تلقائيًا (منطق Fallback بالتطبيق، لا قيد قاعدة بيانات).

**السبب:** فرض إدخال إجباري لكل تركيبة (خدمة × دور) كان سيعني مئات القيم المطلوب إدخالها يدويًا من أول يوم (39+ خدمة × 7+ أدوار) قبل أن يعمل النظام أصلًا — عبء إدخال غير مبرر مقابل الفائدة. نفس فلسفة الرصيد كـLedger (ADR-010): قيمة افتراضية معقولة + استثناءات فقط عند الحاجة.

## ADR-024: منع تعارض الحجز — طبقة مزدوجة (فحص تطبيق + `EXCLUDE constraint` بقاعدة البيانات)

**القرار:** فحص فوري بالتطبيق (تجربة مستخدم، رسالة عربية فورية) **بالإضافة إلى** `EXCLUDE USING gist` بقاعدة البيانات نفسها (يمنع فنيًا تراكب فترتين لنفس الموظف/وحدة المورد، مستثنيًا `cancelled`/`no_show`).

**السبب:** فحص التطبيق وحده معرَّض لـRace Condition حقيقي (موظفتا استقبال تحجزان نفس الموظف بنفس اللحظة تقريبًا، الفحصان "يمرّان" قبل أن يُنجز أي منهما الكتابة). القيد بقاعدة البيانات مضمون رياضيًا بغض النظر عن ترتيب التنفيذ أو أي كود مستقبلي يكتب على نفس الجدول — هذا أهم قرار حماية بيانات بكل المشروع، لأن تعارض حجزين يعني ضررًا تشغيليًا حقيقيًا (زبونان بنفس الموعد).

## ADR-025: سعة المورد (`resources`) — وحدات داخلية مخفية + حلقة إعادة محاولة

**القرار:** مورد بسعة N يُقسَّم داخليًا (تلقائيًا بـTrigger) لـN وحدة مخفية عن المستخدم بالكامل؛ كل وحدة محمية بـ`EXCLUDE constraint` مستقل (نفس منطق ADR-024). عند فشل حجز وحدة (تعارض)، الكود **يعيد المحاولة على الوحدة التالية** بدل الاستسلام الفوري.

**السبب:** Postgres لا يوفر قيدًا جاهزًا لـ"بحد أقصى N متراكبين"؛ تحويل المسألة لـ"N × بحد أقصى واحد" يحلها بنفس الأداة المضمونة. حلقة إعادة المحاولة ضرورية لثغرة مكتشفة أثناء التصميم: القيد يحمي الوحدة، لا اختيار الوحدة — بدونها، فشل حجز وحدة واحدة (بسبب Race Condition) كان يُعلن خطأً "كل الموارد محجوزة" رغم توفر وحدات أخرى فعليًا (رفض حجز صحيح بالغلط).

## ADR-026: منع حجز الوقت الفائت — منطق "الفترة الجارية" + قصّ الوقت عند الحفظ الفعلي

**القرار:** فترة خلصت بالكامل تُمنع كليًا؛ فترة جارية لم تنتهِ بعد تبقى متاحة، لكن وقت البداية الفعلي "يُقصّ" (Trim) للحظة الحفظ الحقيقية (تقريب لأعلى لأقرب دقيقة، لا لأسفل)، ويُعاد القص مرة أخرى عند لحظة الحفظ الفعلية (لا وقت فتح النافذة) لضمان دقة مدة الخدمة بالفاتورة.

**السبب:** منع الوقت الفائت بالكامل (بدون استثناء الفترة الجارية) كان سيرفض حجزًا مشروعًا لزبونة حاضرة الآن. **ترتيب الفحص حاسم:** القص يجب أن يسبق كل فحوصات أخرى (دوام الموظف، تعارض الحجز)، وإلا يُفحص وقت وهمي (الفترة الأصلية قبل القص) بدل الوقت الحقيقي الذي سيُحفظ فعليًا. الفحص بمستوى التطبيق بالكامل، لا قيد قاعدة بيانات (`now()` ليست immutable بـPostgres).

## ADR-027: الحجز المعلّق (`pending_approval`) لتجاوز دوام الموظف — تأكيد بشري + استثناء دوام بتاريخ محدد

**القرار:** بدل المنع الكامل لأي حجز يتجاوز دوام الموظف، حالة حجز جديدة `pending_approval` تُحجز وقتها فعليًا فور الإنشاء (بنفس قوة `booked`، عبر توسيع قيود `EXCLUDE` لتشملها)؛ التأكيد اللاحق (بعد تنسيق هاتفي خارج النظام) يمدّد دوام الموظف **ليوم واحد بالذات فقط** عبر جدول منفصل (`employee_schedule_exceptions`)، دون أي تغيير على نمط الدوام المتكرر.

**السبب:** المنع الكامل تجاهل واقع عمل حقيقي (موظفة قد توافق على تمديد استثنائي). صفوف استثناء متعددة بدل توسيع نافذة واحدة ضروري رياضيًا (توسيع نافذة واحدة عند تأكيدين متتاليين بأوقات متباعدة كان سيفتح اليوم كامل بالخطأ بدل نافذتين منفصلتين). الدالة `confirm_pending_appointment` ذرّية (كتابتان تنجحان أو تفشلان معًا) وتعمل بصلاحيات المستخدم نفسه (`SECURITY INVOKER`، لا `DEFINER`) فتبقى RLS فعّالة. لا نظام إشعارات بُني عمدًا — التنسيق هاتفي بشري بالكامل خارج النظام.

## ADR-028: أسباب الإلغاء (`cancellation_reasons`) — `RESTRICT` لا `SET NULL`، و"لم يحضر" كزر منفصل لا سبب نصّي

**القرار:** سبب إلغاء إجباري (`CHECK` ثنائي الاتجاه بمستوى قاعدة البيانات) من جدول Lookup قابل للإدارة، بحذف `RESTRICT` (لا `SET NULL` كما فعلنا مع الفئة/مصدر الاكتساب)، مع عمود `is_active` كمخرج عملي للـ`RESTRICT`. "لم يحضر" (`no_show`) مستثناة عمدًا من قائمة الأسباب المزروعة — تُعامل كزر إجراء منفصل يحوّل الحالة مباشرة، لا كسبب إلغاء نصّي.

**السبب:** سبب الإلغاء يوثّق حدثًا تاريخيًا وقع بتاريخ محدد (لا يتغيّر أبدًا)، بعكس الفئة/المصدر اللذين يصفان حالة حاضرة قابلة لإعادة التصنيف — حذف سبب مستخدم يعني محو شهادة على واقعة، فالتعطيل هو المسار الصحيح. دمج "لم يحضر" بقائمة الأسباب كان سيدفع موظفة الاستقبال لاختياره (أقرب خيار بقائمة مفتوحة) بدل استخدام حالة `no_show` المخصصة أصلًا، فتبقى فارغة وتقارير عدم الحضور خاطئة بصمت — نفس درس "الفشل الصامت" (ADR سابقة حول رسائل النجاح).

## ADR-029: تجميع تراكب العرض بخانة الموظف — إعادة استخدام منطق عام، لا مكوّن واجهة خاص بالموارد

**القرار:** دالة `clusterAppointments` (مبنية أصلًا لعمود المورد) أُعيد استخدامها بدون أي تعديل لخانة الموظف أيضًا (منطقها عام: تجميع أي حجوزات متراكبة زمنيًا، بلا علاقة بمفهوم "مورد"). لكن نافذة العرض بُنيت من جديد (`AppointmentClusterDialog`) بدل إعادة استخدام `ResourceBookingsDialog`.

**السبب:** عمود المورد "للعرض فقط" بتصميمه (قرار سابق)، بينما عمود الموظف يحمل أفعالًا حقيقية (تأكيد/إلغاء/لم يحضر) يجب أن تبقى شغّالة. إعادة استخدام نافذة العرض الثابتة كانت ستُفقِد وظيفة حقيقية لصالح توحيد كود غير مبرر — الدرس العام: **"إعادة الاستخدام" هدفها تجنّب تكرار غير ضروري، لا تجنّب بناء شيء جديد حين يكون مختلفًا وظيفيًا فعلًا**، حتى لو تشابه بصريًا مع شيء موجود.

## ADR-030: إعادة الجدولة — سجل جديد مرتبط لا تعديل مباشر، مع حل التبعية الدائرية بـ`DEFERRABLE`

**القرار:** إعادة جدولة حجز تُنشئ **صفًّا جديدًا** وتحوّل القديم لحالة `rescheduled` (بوقته الأصلي كما هو)، مرتبطين بعمود `rescheduled_to_id` **على الصف القديم فقط**. الترتيب داخل معاملة ذرّية: **قلب القديم أولًا، ثم إدراج الجديد**. والمفتاح الأجنبي للرابط `DEFERRABLE INITIALLY DEFERRED`.

**السبب — ثلاث طبقات مترابطة:**
1. **لماذا سجل جديد لا تعديل:** الحجز الأصلي سجل تاريخي؛ تعديل وقته مباشرة يمحو أنه نُقل أصلًا (نفس فلسفة `cancelled`/`RESTRICT`). واتجاه واحد للرابط لأنه **الاتجاه القابل للحماية بقيد `CHECK`** — لو كان المؤشّر على الصف الجديد، لا يمكن كتابة قيد يفرض "يجب أن يشير صف آخر لهذا الصف".
2. **لماذا القلب قبل الإدراج ("مصيدة الترتيب"):** نقل حجز نصف ساعة لنفس الموظف (10:00-11:00 → 10:30-11:30) هو **أشيع سيناريو سحب ممكن**؛ لو أُدرج الجديد أولًا، القديم لا يزال شاغلاً وقتَه فيرفض القيد الحجز **وهو ينتقل قريبًا من نفسه** — أبسط استخدام يومي كان سينكسر.
3. **لماذا `DEFERRABLE` على المفتاح وحده:** القلب أولًا يخلق تبعية دائرية حقيقية (القيد يفرض وجود الرابط، والرابط يشير لصف لم يوجد بعد). الحل: توليد `UUID` مسبقًا + تأجيل **فحص وجود الصف المُشار إليه فقط** لإغلاق المعاملة. **قيد الرابط يبقى فوريًا** — تأجيله كان سيسمح بصف `rescheduled` بلا رابط أثناء أي معاملة، أي الفساد الصامت نفسه الذي بُني العمود لمنعه. و`ON DELETE RESTRICT` يبقى فعّالًا عمليًا حتى مع `DEFERRABLE` (عمليات الحذف المفردة بمعاملاتها الخاصة).

**قواعد مصاحبة:** الخدمة والمدة ثابتتان (تغيير الخدمة = حجز مختلف، لا إعادة جدولة)؛ حالة الصف الجديد تُحدَّد من الوقت الجديد وحده لا موروثة؛ استثناء دوام الحجز القديم يُحذف (تبريره زال)؛ **رفض تام** لعدم تطابق دور الموظف مع الخدمة (حقيقة مهنية) مقابل **تحذير قابل للتجاوز** لخارج الدوام (سؤال بشري).

## ADR-031: مدخلان لنفس العملية — توحيد المنطق **ورسائل الخطأ** بمصدر واحد

**القرار:** زر "إعادة جدولة" (نافذة) والسحب والإفلات يستخدمان `lib/rescheduleFlow.js` (`planReschedule`/`commitReschedule`) حرفيًا — **بما في ذلك جدول رسائل الخطأ المشترك**. والمنطق العام للحفظ استُخرج إلى `lib/bookingPlacement.js` + `lib/placementIO.js`، **وحُوِّلت نافذة الحجز القائمة عليهما أولًا قبل بناء أي ميزة جديدة فوقهما**.

**السبب:** توحيد المنطق وحده غير كافٍ — لو بقيت رسائل الخطأ منفصلة، أي تعديل مستقبلي على نص رسالة بمدخل واحد يُنسى بالآخر، فيفسّر المدخلان نفس الرفض بكلمتين مختلفتين ("الانجراف الصامت"، أصعب أنواع الأخطاء اكتشافًا). وتحويل المسار القائم على الطبقة الجديدة **قبل** البناء فوقها يضمن أنها مُثبتة بمسار حقيقي معروف السلوك، لا مُختبرة لأول مرة مع ميزة جديدة (فلو ظهر خلل، مصدره واضح).

**استثناء متعمّد واحد:** نافذة تأكيد السحب تفحص لحظة **الفتح** لا عند "تأكيد" — لأن عمود الإفلات يحدد الموظف سلفًا، فرفض الدور مؤكَّد قبل أي ضغطة، وإظهاره فورًا أصدق من زر لن ينفع.

**درس منهجي من التحقق:** فشل ظاهري بخطوة اختبار واحدة تبيّن أنه **غموض بسؤال الاختبار** لا خلل بالتصميم (كان يحجز نطاقًا يتقاطع مع الحجز الجديد نفسه). **الدرس: اختبار غامض السؤال ليس دليل فشل** — يُصحَّح الاختبار لا الكود، بعد إثبات السبب رياضيًا.

## ADR-032: موظف إضافي على نفس الحجز — صفوف مترابطة بـ`group_id` self-referencing، لا جدول علاقة

**القرار:** كل موظف مشارك بجلسة (أساسي أو إضافي) هو **صف كامل بجدول `appointments` نفسه**، لا سطر بجدول علاقة منفصل. تجميع الصفوف عبر `group_id` (يساوي `id` نفسه للصف الأساسي)، مع `is_primary` وقيدين يفرضان أساسيًا واحدًا بالضبط لكل مجموعة.

**السبب:** `EXCLUDE USING gist` يفحص صفوفًا **داخل نفس الجدول فقط**. جدول علاقة منفصل للمشاركين يعني تكرار `start_time`/`end_time` فيه ليصبح قابلاً للفحص — أي **حقيقتان لنفس الشيء قابلتان للاختلاف** (نفس السبب الذي رفضنا لأجله `rescheduled_at` منفصلاً بـADR-030). **الدليل الحاسم أن هذا النمط مطبَّق أصلًا:** `resource_unit_id` بُني على `appointments` نفسه من المرحلة 4 لنفس السبب بالضبط.

**لماذا `group_id = id` (self-reference) بدل `DEFERRABLE` كما في `rescheduled_to_id`:** الصف الأساسي يشير **لنفسه**، فيوجد فورًا وقت إدراجه — لا تبعية دائرية زمنية (بعكس إعادة الجدولة حيث يُشار لصف لم يوجد بعد). **النتيجة العملية الأهم (مؤكَّدة بفحص أمان صريح):** صفر تعديل على قيدَي منع التعارض — كل مشارك محمي تلقائيًا لمجرد كونه صفًّا عاديًا بالجدول، بما يشمل سيناريو كان سيفلت من جدول علاقة (موظف "مساعد" بجلسة ومشغول فعليًا بجلسة أخرى بنفس اللحظة).

**ثلاث دوال قائمة عُدِّلت بنفس لحظة التغيير البنيوي، لا لاحقًا:** قرار "انتشار كل الحالات على المجموعة كاملة" يكسر الدوال المبنية على افتراض "صف واحد" من أول استخدام فعلي؛ التوافق العكسي الكامل (نفس التوقيع، كل حجز قديم "مجموعة من عضو واحد") ضمن صفر خطر على الإنتاج القائم.

**اكتشاف تراكمي لاحق (`remove_participant`، مصمَّمة، مؤجَّلة التنفيذ):** بما أن `cancel_appointment` تنشر الإلغاء على المجموعة كاملة بذرّية واحدة، فحالة أي صف مشارك تصبح **مرآة موثوقة** لحالة الجلسة كلها — فحص حالة الصف الممرَّر وحده كافٍ، بلا حاجة لفحص منفصل للأساسي. **هذا مثال مباشر على كيف توفِّر قرارات بنيوية سابقة صحيحة تعقيدًا لاحقًا بشكل تراكمي**، لا صدفة معزولة.

## ADR-033: `AuthGate` — حماية بنيوية دائمة ضد فقدان الحالة المحلية، لا سد لثغرة معزولة

**القرار:** بعد إصلاح المُحفِّز المعروف الوحيد (كائن `session` غير مستقر المرجع من Supabase باعتمادية `useEffect`)، بُني مكوّن `AuthGate` واحد يُطبَّق على كل الصفحات الست، يميّز بين "نفس هوية المستخدم" (لا يهدم الشجرة) و"هوية تغيَّرت فعلاً" (يهدم ويعيد البناء عن قصد).

**السبب:** المسح الشامل (51 اعتمادية عبر 34 ملفًا، بمعيار "مصدر التغيّر: فعل داخلي أم حدث خارجي غير متحكَّم به؟") وجد مكانًا واحدًا فقط مصابًا. **رغم النتيجة النظيفة، تقرر بناء الحماية العامة أيضًا** — لأن أي حالة `loading` مستقبلية تُبنى مع ميزة جديدة قد تقع بنفس الفخ دون أن تخضع لنفس دقة الفحص هذه المرة. **نفس فلسفة `RESTRICT`/`EXCLUDE constraint` بقاعدة البيانات مطبَّقة الآن على مستوى الواجهة**: لا الاعتماد على يقظة فحص يدوي متكرر، بل قيد بنيوي يمنع الفئة كاملة من الأخطاء من جذرها، مهما كان مصدرها المستقبلي.

**قيد تقني واجهه التنفيذ:** صفحة `/clients/[id]` (الأعقد حالةً) تطلَّبت إبقاء كل الـHooks خارج الـrender-prop تمامًا — استدعاء Hooks بشكل مشروط داخل render-prop يخالف قاعدة React الأساسية (ترتيب ثابت للاستدعاء).

**درس منهجي:** الفرق بين "الاعتمادية تتغيّر" و"لماذا تتغيّر" (فعل داخلي متحكَّم به مقابل حدث خارجي بتوقيت خارجي) هو المعيار الذي حدَّد الحل الصحيح (تثبيت مرجع لمُحفِّز واحد + حماية بنيوية عامة)، لا افتراضًا أوليًا لسبب المشكلة (Remount عام بسبب Focus).

## ADR-034: هوية دالة PostgreSQL عند `CREATE OR REPLACE` — عدد/أنواع المعاملات فقط، لا القيم الافتراضية

**الدرس (عام، قابل لإعادة الحدوث بأي دالة مستقبلية):** إضافة معامل جديد لدالة موجودة، حتى بقيمة افتراضية وبآخر القائمة، **لا تضمن استبدال (Replace) الدالة القديمة** — PostgreSQL يحدِّد هوية الدالة حصرًا بعدد وأنواع معاملاتها (بحسب توثيق Postgres الرسمي)، لا بوجود قيم افتراضية. دالة بستة معاملات ودالة بسبعة (السابع افتراضي) **دالتان مختلفتان تمامًا** من منظور التخزين، حتى لو الفرق مجرد معامل اختياري.

**كيف تجلّى الخطأ عمليًا:** أثناء إضافة `p_reschedule_reason_id` لدالة `reschedule_appointment`، اعتُقد أن الإضافة بآخر القائمة بقيمة افتراضية كافية لضمان الاستبدال الآمن (بناءً على فهم لتوثيق حل الاستدعاء/Overload Resolution، طُبِّق خطأً على هوية التخزين). النتيجة: نسختان متزامنتان من الدالة (فحص `select count(*) from pg_proc where proname = '...'` أظهر `2` بدل `1` المتوقَّع)، وكود الواجهة القائم — الذي ينادي الدالة بستة معاملات مسمَّاة تطابق كلا النسختين — وقع بحالة **استدعاء غامض (Ambiguous function call)**، فتعطَّلت إعادة الجدولة فعليًا حتى اكتُشف الخلل وحُذف التوقيع القديم صراحةً بأنواع معاملاته بالضبط.

**الإجراء الوقائي العام لأي تعديل مستقبلي على دالة قائمة:** بعد أي `CREATE OR REPLACE FUNCTION` يضيف/يحذف معاملاً، تحقَّق دائمًا بـ`select count(*) from pg_proc where proname = 'اسم_الدالة'` — القيمة المتوقَّعة **1 دائمًا** إلا إذا كان تعدد النسخ (Overload) مقصودًا صراحةً.

## ADR-035: تعديل نهاية جلسة جارية — حالة `adjusted` مستقلة تشارك مؤشّرًا محايدًا، بصفر إعادة استخدام لمنطق الحجز الجديد

**القرار:** حالة `appointment_status` جديدة (`adjusted`) لتمديد أو إنهاء مبكر لجلسة `booked` قائمة فعلاً، منفصلة عن `rescheduled` لكن تشارك معها عمود الربط بعد إعادة تسميته لاسم محايد (`superseded_by_id`). الدالة (`adjust_appointment_duration`) **تتجاهل عمدًا** كل منطق فحص الحجوزات الجديدة (حارس الوقت الفائت، حلقة إعادة محاولة وحدات المورد، تحذير خارج الدوام كطلب موافقة).

**السبب:**
- **حالة منفصلة عن `rescheduled`:** جلسة "حدثت جزئيًا ثم انتهت بوقت مختلف" مفهوم مختلف جوهريًا عن "لم تحدث إطلاقًا بهذا الوقت" — دمجهما يفسد أبسط مقياس تشغيلي ("كم جلسة اكتملت فعليًا؟")، بنفس المنطق الذي حكم فصل `no_show` عن أسباب الإلغاء العادية.
- **مؤشّر مشترك بعد إعادة تسمية، لا مؤشّر ثانٍ منفصل:** المعنى المجرَّد ("هذا الصف حلّ محلّه صف آخر") صحيح للحالتين معًا؛ التحقق المسبق (صفر كود يقرأ الاسم القديم) جعل إعادة التسمية الآن أرخص من الاحتفاظ بمؤشّرين متوازيين لنفس المفهوم — وورَّث تأجيل المفتاح الأجنبي الجاهز أصلاً بدل بناء تأجيل جديد لنفس مصيدة الترتيب (الصف الجديد يتداخل حتمًا مع القديم).
- **تجاهل متعمَّد لمنطق الحجز الجديد، لا إعادة استخدامه:** حارس الوقت الفائت مصمَّم لمنع حجز جديد بالماضي — لا معنى لتطبيقه حين تكون بداية الجلسة بالماضي بالتعريف (الجلسة بدأت فعلاً). البحث عن وحدة مورد/موظف بديل عبثي فيزيائيًا حين تكون الزبونة حاضرة فعلاً بمكانها. "خارج الدوام" هنا توثيق واقعة حدثت (الموظفة استمرت وقتًا إضافيًا)، لا طلب موافقة مسبقة على شيء لم يحدث بعد.

**درس تقني عام إضافي (يوسِّع ADR-034):** إعادة تسمية عمود عبر `RENAME COLUMN` تُحدِّث القيود تلقائيًا (تشاور بالرقم الداخلي للعمود) لكن **لا** تُحدِّث أجسام دوال PL/pgSQL القائمة (تُخزَّن كنص خام يُحلّ وقت التنفيذ، وتشاور بالاسم) — أي إعادة تسمية عمود تستخدمه دالة موجودة تتطلب إعادة إنشاء تلك الدالة صراحةً بنفس التوقيع، وإلا تنكسر بصمت عند أول استدعاء.

## ADR-036: إضافة عمود `NOT NULL` بلا قيمة افتراضية تتطلب مسح **كل** مسارات الإدراج بالكود، لا فقط المسار قيد التعديل

**الدرس (عام، اكتُشف عبر انحدار حقيقي حدث فعلاً):** عند إضافة `group_id`/`is_primary` بميزة "موظف إضافي" (ADR-032)، حُدِّث مسار الحجز العادي (`AppointmentFormDialog`) ليمرّر القيمتين الجديدتين صراحة — لكن **مسار إدراج منفصل تمامًا** (إضافة زبون لقائمة الانتظار، بلا موظف ولا وقت) بقي غير مُحدَّث، لأنه **لم يكن ضمن نطاق التعديل المباشر وقتها ولا ضمن أي اختبار يدوي فوري**. النتيجة: كل محاولة إضافة لقائمة الانتظار كانت تفشل بصمت بخطأ `not_null_violation` — منذ لحظة دمج ميزة الموظف الإضافي وحتى اكتشافه لاحقًا بخطوة تحقق استباقية قبل بناء ميزة جديدة فوق ذلك المسار.

**لماذا لم يُكتشف فورًا:** الاختبارات الآلية (170+ اختبارًا وقتها) لم تغطِ هذا المسار تحديدًا، والتجربة اليدوية بعد دمج ميزة الموظف الإضافي ركّزت على السيناريوهات ذات الصلة المباشرة (حجز بموظفين، الفلترة، التجميع البصري) لا على كل مسار إدراج آخر بالتطبيق بشكل منهجي.

**الإجراء الوقائي العام لأي عمود `NOT NULL` جديد بلا قيمة افتراضية مستقبلاً:** قبل اعتبار الميزة مكتملة، **مسح صريح لكل نقاط الإدراج (`insert`) على الجدول المتأثر عبر الكود كله** (بحث نصي عن اسم الجدول، لا الاكتفاء بمسار الميزة الجديدة فقط) — بنفس روح المسح الشامل الذي طُبِّق سابقًا لاعتماديات `useEffect` غير المستقرة (ADR-033). **حدس طلب "خطوة تحقق أولاً" قبل بناء ميزة جديدة فوق مسار قديم** هو ما كشف هذا الانحدار تحديدًا — درس إضافي: أي مسار كود قديم لم يُلمس منذ فترة طويلة يستحق تحققًا سريعًا قبل البناء فوقه مباشرة، لا افتراض سلامته لمجرد عدم ظهور شكوى.

## ADR-037: لا يُجمَع تعديل بنيوي دائم (DDL) مع معاملة اختبار تُرجَع بـ`RAISE EXCEPTION` بنفس السكربت — ومسار واحد ناجح لا يثبت سلامة دالة كاملة

**الدرس الأول (اكتُشف عبر سلسلة تصحيح طويلة ومربكة):** سكربت جمع بين `CREATE OR REPLACE FUNCTION` (تعديل دائم) وفحص تحقق ينتهي بـ`RAISE EXCEPTION` لإرجاع كل شيء — لكن `RAISE EXCEPTION` **يُرجع المعاملة كاملة، بما فيها الـ`DDL` نفسه**. النتيجة: الإصلاح **بدا** ناجحًا وقت التنفيذ (رسالة تحقق إيجابية)، بينما الجسم القديم المكسور **بقي حيًّا فعليًا** بقاعدة البيانات — ما فسّر استمرار نفس الخطأ (`42804`) من الواجهة رغم "نجاح" الإصلاح المتكرر ظاهريًا. **القاعدة الثابتة الآن:** أي `DDL` دائم يُراد حفظه لا يُجمَع أبدًا بنفس السكربت مع اختبار يُرجَع عمدًا؛ يُستخدم نمط "معاملة فرعية" (Savepoint) للاختبار المعزول، أو سكربطان منفصلان تمامًا.

**الدرس الثاني (ذو صلة، يفسّر لماذا لم يُكتشف الخلل الأول فورًا):** PL/pgSQL يخطِّط كل جملة SQL داخل جسم الدالة **أول مرة تُنفَّذ فعليًا** لا وقت إنشاء الدالة — فنجاح مسار تنفيذ واحد (مثلاً `p_provisional = false` بلا مشاركين) **لا يثبت شيئًا** عن مسارات أخرى بنفس الدالة (حلقة معالجة مشاركين بـ`CASE` منفصلة، فرع `pending_approval`) لم تُنفَّذ ولو مرة. **القاعدة:** اختبار دالة تحتوي فروعًا شرطية يتطلب تنفيذ **كل** المسارات فعليًا، لا الاكتفاء بنجاح المسار الأول المجرَّب.

**أربع فخاخ متجاورة صعَّبت رؤية السبب الجذري** (موثَّقة تفصيليًا بـ`CLAUDE.md`، لا تُكرَّر هنا): فحص وجود الدالة بعدّ نُسخها لا بمحتواها الفعلي؛ هشاشة المطابقة النصية الحرفية بفحوصات البيانات (استخدام `LIKE` بدل `=` يتفادى هذا)؛ هوية دالة Postgres محكومة بعدد/أنواع المعاملات فقط (ADR-034)؛ وتخطيط PL/pgSQL المتأخر لكل جملة (أعلاه).

**قرار توثيقي مهم:** أُنشئ ملف **`CLAUDE.md` بجذر المستودع نفسه** — أول بند فيه هذه القاعدة بالضبط. هذا الملف **يعيش داخل الكود مباشرة**، فيصل تلقائيًا لأي جلسة Claude Code مستقبلية دون الحاجة لإعادة إرساله ضمن ملفات التسليم الأربعة الخارجية (`PROJECT_HANDOFF.md` وأخواتها) — الاثنان متكاملان لا متكرران: ملفاتنا الأربعة توثّق **"لماذا" القرارات المعمارية** لصالح استمرارية الجلسات، بينما `CLAUDE.md` يوثّق **قواعد كتابة سكربتات SQL العملية** ليقرأها Claude Code فور بدء أي عمل بالمستودع.

## ADR-038: عمليات المجموعة (الحجز متعدد الموظفين) تُكتب بنطاق موجب دائمًا — لا حارس سالب

**الدرس (اكتُشف عبر ميزة `remove_participant`، عام لأي عملية جماعية مستقبلية):** الدوال الأربع القائمة على مجموعات حجز (`cancel_appointment`, `reschedule_appointment`, `mark_no_show`, `adjust_appointment_duration`) كانت جميعها مكتوبة بحارس **سالب** (`status not in (...)` لرفض الحالات غير المرغوبة). حين أُضيفت حالة جديدة ممكنة داخل المجموعة (عضو `cancelled` بعد إزالته فرديًا، بينما البقية فاعلة)، **كل الحراسات السالبة رفضت العملية تلقائيًا** على كامل المجموعة — الجلسة "تتجمَّد": لا يمكن إلغاؤها، ولا إعادة جدولتها، ولا تمديدها، بمجرد وجود عضو واحد بحالة لم تكن متوقَّعة وقت كتابة الحارس السالب. الدالة الوحيدة الناجية (`confirm_pending_appointment`) كانت الاستثناء الذي أكَّد القاعدة: هي الوحيدة المكتوبة بنطاق **موجب** (`status = 'pending_approval'` — اعمل على هذا فقط)، فتجاهلت الأعضاء الآخرين طبيعيًا دون أي تعديل.

**القاعدة الثابتة لأي دالة جماعية مستقبلية:** تُكتب دائمًا بنطاق **موجب** ("اعمل على الأعضاء الفاعلين تحديدًا: `status in ('booked', 'pending_approval')`")، لا بحارس سالب ("ارفض كل ما ليس متوقَّعًا"). النطاق الموجب يتجاهل حالات مستقبلية غير متوقَّعة بأمان (يستبعدها من المعالجة دون رفض العملية كلها)، بينما الحارس السالب يفشل بصمت أمام أي حالة جديدة لم تكن بذهن الكاتب وقت الكتابة — وهذا فرق حاسم أثبتته المقارنة المباشرة بين الأنماط الخمسة الموجودة فعليًا بنفس قاعدة الكود.

## ADR-039: فحص "محتوى" دالة قبل `CREATE OR REPLACE` يجب أن يشمل خصائص التشغيل، لا الجسم فقط

**الدرس (امتداد مباشر لقانون `CLAUDE.md` الثاني "افحص المحتوى لا الوجود"، اكتُشف أثناء تعديل دالة زرع أسباب إلغاء افتراضية):** `prosrc` (نص جسم الدالة) **لا يعرض** خصائص تشغيل حاسمة مثل `SECURITY DEFINER` أو `SET search_path`. `CREATE OR REPLACE FUNCTION` يُصفِّر **كل** خاصية غير مذكورة صراحة بالجملة الجديدة — لا الجسم فقط. لو أُعيدت كتابة دالة بناءً على `prosrc` وحده (بافتراض أن الجسم يمثّل "كل" ما يلزم معرفته)، وكانت الدالة الأصلية `SECURITY DEFINER`، فإعادة الإنشاء بدونها تُسقطها بصمت.

**لماذا كانت هذه الحالة خطيرة تحديدًا:** الدالة المتأثرة تعمل ضمن مشغّل `AFTER INSERT ON salons` — لحظة إنشاء صف الصالون، سياق المستخدم (`profiles.salon_id`) غالبًا لا يشير بعد إلى الصالون الجديد، فتفشل سياسات RLS العادية دون صلاحيات مرفوعة. فقدان `SECURITY DEFINER` بصمت كان سيكسر **إنشاء كل صالون جديد من تلك اللحظة فصاعدًا** — عطل لا يظهر إلا عند أول محاولة تسجيل صالون حقيقي بعد النشر، لا وقت التطوير.

**الإجراء الوقائي العام لأي تعديل مستقبلي على دالة قائمة:** الفحص قبل `CREATE OR REPLACE` يجب أن يستخدم `pg_get_functiondef(oid)` (يُرجع التعريف الكامل: اللغة، `SECURITY DEFINER`/`INVOKER`، `search_path`، وكل الخصائص) لا `prosrc` وحده (يُرجع الجسم فقط). عند عدم اليقين من خاصية معيّنة، فحص ذاتي صريح قبل التنفيذ (استعلام يتحقق من القيمة الفعلية بعد الاستبدال) أضمن من الاستنتاج المنطقي وحده، مهما بدا الاستنتاج متماسكًا.
